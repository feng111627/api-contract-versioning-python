# API Contract Versioning（Python / FastAPI）

一套“接口版本兼容 + 自描述文档”的示例服务：接口迭代后，老调用方与新调用方都能拿到
**可预期、可解释**的结果。

- 多版本同时在线，版本生命周期状态集中登记（在线 / 已废弃 / 已下线）
- 已下线版本返回 `410 VERSION_RETIRED`，未知版本返回 `404 VERSION_UNKNOWN`，
  与“版本正确但路径不存在”的 `404 RESOURCE_NOT_FOUND` 可区分
- 参数校验、业务异常、内部异常统一归一化为同一个错误信封与稳定错误码
- 内部异常只返回固定文案，绝不透出异常类型、堆栈或内部信息
- 从路由与 Pydantic 模型自动生成确定性（字节级可复现）的接口契约文档，
  每个版本独立成节，历史契约不会被新版本覆盖

## 版本策略

版本通过路径前缀显式声明：`/v1/...`、`/v2/...`。所有版本在
`app/main.py::build_registry()` 中集中登记，登记信息（状态、废弃日期、下线日期、
后继版本、说明）本身就是对外契约。

| 版本 | 状态 | 引入 | 废弃自 | 计划下线 | 后继 |
|------|------|------|--------|----------|------|
| v0 | `retired` 已下线 | 2023-01-01 | 2024-06-01 | **2025-01-01** | v1 |
| v1 | `deprecated` 已废弃 | 2024-01-01 | 2026-10-06 | **2027-04-01** | v2 |
| v2 | `active` 推荐 | 2026-10-06 | — | — | — |

### 访问控制规则

| 情况 | HTTP | 错误码 | 说明 |
|------|------|--------|------|
| 访问已下线版本（如 `/v0/...`） | 410 | `VERSION_RETIRED` | 任意方法、任意路径一致拒绝；带后继版本 `Link` 头 |
| 访问未登记版本（如 `/v9/...`） | 404 | `VERSION_UNKNOWN` | 明确是“版本不对”，不是普通路由缺失 |
| 已知版本下路径不存在（如 `/v2/x`） | 404 | `RESOURCE_NOT_FOUND` | 版本正确、资源/路径不对 |
| 已废弃版本（v1） | 200 | — | 继续正常服务 |

废弃版本的响应自动带上标准提示头，调用方可机器识别并安排迁移：

- `Deprecation`：废弃声明日期（HTTP-date）
- `Sunset`：计划下线日期（RFC 8594）
- `Link: /v2; rel="successor-version"`：后继版本
- `X-Api-Version`：本次命中的版本

### 废弃的三个层级

1. **版本级**：v1 整体 deprecated —— 由中间件统一注入响应头，文档标记状态。
2. **接口级**：`GET /v2/reports/legacy-summary` 端点标记 `deprecated=True`，
   OpenAPI/契约文档中带废弃标记。
3. **字段级**：v2 响应中的 `email` 与请求中的 `name`（v1 风格兼容入参）
   通过 Pydantic `deprecated=True` 标记，schema 中带 `deprecated` 与 `sunset`。

## 兼容范围与演进纪律

以 `users` 资源为例：

- **v1（冻结）**：`UserV1 { id, name, email }`。只允许修缺陷，不允许新增必填字段、
  改字段语义或改既有错误码。
- **v2（演进）**：`UserV2 { id, first_name, last_name, tier, email? }`
  - `name` 拆成 `first_name` / `last_name`（结构性变更 → 新版本）
  - 新增可选层级字段 `tier`
  - 兼容期内容忍 v1 风格的 `name` 入参，服务端自动拆分，并通过 `Deprecation`
    响应头提示迁移；`name` 与拆分字段互斥，同时提供返回 `BAD_REQUEST`
- 两个版本读同一数据源，差异只体现在契约层；v1 的文档与响应永远保持 v1 形状，
  不会被 v2 覆盖。

允许的向后兼容变更（不升版本）：新增可选字段、新增端点、放宽校验、修复缺陷。
破坏性变更（必升版本）：删除/重命名字段、改字段类型或语义、收紧必填约束、
改变错误码语义。

## 统一错误结构

所有错误（任何版本）都返回同一信封：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数校验失败。",
    "details": [
      {"field": "name", "issue": "String should have at least 1 character"}
    ]
  }
}
```

- `details` 仅在有字段级明细或补充信息时出现；错误信封只有
  `error.code` / `error.message` / 可选 `error.details`。
- 校验明细只保留字段位置与问题描述，剔除原始输入等内部上下文。

| 错误码 | HTTP | 触发场景 |
|--------|------|----------|
| `VERSION_RETIRED` | 410 | 访问已下线版本 |
| `VERSION_UNKNOWN` | 404 | 访问未登记版本 |
| `VALIDATION_ERROR` | 422 | 请求体/参数的框架层校验失败 |
| `BAD_REQUEST` | 400 / 405 | 业务规则失败 / 方法不允许 |
| `RESOURCE_NOT_FOUND` | 404 | 资源不存在或已知版本下路径不存在 |
| `CONFLICT` | 409 | 与资源状态冲突（预留） |
| `RATE_LIMITED` | 429 | 限流（预留） |
| `INTERNAL_ERROR` | 500 | 未预期内部异常；**响应体固定，细节仅进服务端日志** |

## 自描述文档

- 在线契约：`GET /docs/contract`
- 版本总览：`GET /`（含各版本状态与下线日期）
- 快照文件：`docs/contract.json`（提交到仓库）

文档完全由代码生成：扫描实际注册的路由（方法/路径/摘要/废弃标记）与 Pydantic
模型的 JSON Schema，并附带统一错误信封 schema 与全部错误码表。输出做了
键排序与固定缩进，同一份代码多次生成**字节级一致**；每个版本独立成节，
已下线版本保留版本元数据与下线拒绝策略说明。

重新生成快照：

```bash
uv run python -c "from app.main import create_app; create_app(write_snapshot='docs/contract.json')"
```

31 个用例按业务场景分组，日志中可直接看到每条用例覆盖的场景与说明：

- **版本兼容**（5）：v1 旧字段保留、v2 字段拆分与新增字段、跨版本数据共享、
  旧入参兼容、互斥边界
- **版本废弃声明**（5）：版本级/接口级/字段级废弃标记、标准响应头、下线日期
- **版本下线与拒绝**（4）：410 一致性、任意方法拒绝、404 双码区分、
  非版本路径不受影响
- **校验错误归一化**（5）：缺字段、约束失败跨版本一致性、错误请求体、
  业务规则冲突、信封形态稳定
- **业务异常归一化**（2）：资源缺失跨版本同码、405 归一化
- **内部异常防泄漏**（2）：500 固定信封、响应体无类型/堆栈/密钥
- **文档自描述/可复现/历史契约保护**（8）：端点清单、废弃状态、错误码表、
  字节级确定性、与提交快照一致、v1/v2 契约互不覆盖
